# Security Policy

If you believe you've found a security vulnerability in yt-dlp, we encourage you to report it to us privately via [GitHub's vulnerability reporting](https://github.com/yt-dlp/yt-dlp/security/advisories/new).

## LLM / AI Policy

The yt-dlp project has a strict ["No AI / No LLM" policy](https://github.com/yt-dlp/yt-dlp/blob/master/CONTRIBUTING.md#no-ai--no-llm-policy) for its contributors.
However, an exception is made for the discovery of security vulnerabilities made via LLM or AI-assistance.
If you've found a security issue in yt-dlp, we want to know about it and we want to fix it, regardless of how you found it.

We do **not** want reports coming directly from an LLM agent.
An acceptable security report has been validated and proofread by a human.
You must understand the vulnerability you are reporting well enough to explain it in your own words.
(Ideally, the entire report would be written by you, the human.)
If you aren't able to answer questions about your report, we may have to reject and close it.

Furthermore, all security reports must follow the guidelines listed below.

## Security Report Guidelines

1. A valid security issue must be reproducible on the latest commit in the development branch (`master`).
2. If the "vulnerability" is a documented behavior of the program, then it's **not a security vulnerability**. If the documentation is insufficiently communicating the risk(s) of some documented behavior, then this is a *documentation bug* and should be reported publicly as such.
3. If the impact of the vulnerability is *availability only* (e.g. if the vulnerability is a ReDoS or memory DoS), then **we do not consider it a security vulnerability**, and it should be reported publicly as a bug instead.
4. Misuse of yt-dlp's Python API is **not a security vulnerability in yt-dlp**; it is a vulnerability in the external script or software that is misusing yt-dlp's API.
5. Uncaught exceptions are **not considered security vulnerabilities** in yt-dlp, and we don't even consider them to be reportable bugs unless they can be encountered by the end-user.
6. The `--exec` option allows the user to run shell commands while yt-dlp is mid-operation. If the proof of concept for the "vulnerability" involves a user-provided shell command that would be dangerous or harmful if used directly in the user's shell, then it is **not a security vulnerability.**
7. Any input given to the `--load-info-json` option is expected to have been generated by yt-dlp's `--write-info-json` functionality, and thus it's expected to have been sanitized by yt-dlp at the time of writing. We do not consider manually crafted `--load-info-json` input to be a valid attack vector; if the "vulnerability" cannot be demonstrated without using manually crafted `--load-info-json` input, then it is **not a security vulnerability.**
8. Any proof of concept for a security flaw unrelated to `--load-info-json` must not depend on that option.

Any security reports that do not follow the above guidelines will be rejected and closed. A reporter who repeatedly violates one or more of these guidelines may be permanently blocked from the yt-dlp organization.
